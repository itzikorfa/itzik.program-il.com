This site looks like a terminal, but behind it is a small, deliberate set of AWS and GitHub services. This post walks through each piece: what it does, and **why I picked it** over the alternatives. The short version: keep the site static, keep the moving parts few, and make every part cost close to nothing.

## The big picture

```
          you (browser)
               │
     itzik.program-il.com ──── Route 53 (DNS)
               │
        AWS Amplify Hosting ── CDN + HTTPS certificate
               │  builds from
        GitHub repository ──── GitHub Actions (daily rebuild)
               │                /admin editor (posts, links)
               │
   favorites form ──► Lambda function ──► SES (confirmation email)
                          │    │
                          │    └─► DynamoDB (rate limits)
                          └──────► GitHub pull request ──► I review & merge
```

Two halves:

1. **The site itself is static.** Every page is plain HTML built ahead of time. There's no server, no database, and nothing to patch.
2. **One tiny backend** exists only for the "suggest a link" form, because that's the one feature that has to receive data from visitors.

## The site: Astro, built ahead of time

The pages are generated by **[Astro](https://astro.build/)**. My blog posts are Markdown files, the "worth reading" and "favorites" lists are small YAML files, and my GitHub projects are pulled from the GitHub API at build time.

**Why static?**

- **Security.** A static site has almost no attack surface. There's no login on the public site, no database to leak, and no server code running per visit.
- **Speed.** Pages are served from a CDN close to the reader.
- **Cost.** Serving files is nearly free.

**Why Astro** and not a blog platform (WordPress, Medium) or a single-page React app? Astro outputs plain HTML with very little JavaScript, it reads Markdown natively, and it checks the content against a schema on every build. A broken post fails the build instead of breaking the live site.

The site is also written to be **AI-friendly**: it publishes [`llms.txt`](/llms.txt) (a plain-text summary for AI assistants), a Markdown copy of every post, structured data about me, and a sitemap. AI *search* bots may read it. AI *training* crawlers are blocked in `robots.txt` for now.

## Hosting: AWS Amplify Hosting

**What it does:** Amplify watches the GitHub repository. Every time something lands on the `main` branch, it builds the site and publishes it to a CDN (it uses Amazon CloudFront underneath), with an HTTPS certificate it renews automatically.

**Why Amplify** and not the classic "S3 bucket + CloudFront + certificate + build pipeline" setup? That classic setup is four or five services I'd have to wire together and maintain myself. Amplify gives me the same result as one service: build on push, CDN, HTTPS, custom domain, redirects and security headers.

Things I configure in Amplify:

- **Redirects.** `program-il.com` and `www.program-il.com` send you here with a *temporary* redirect, so the main domain stays free for future projects.
- **A custom 404 page**, the "command not found" page.
- **Security headers** (in a `customHttp.yml` file in the repo):
  - HSTS forces HTTPS.
  - `X-Frame-Options` and `frame-ancestors` stop other sites from embedding mine.
  - `Permissions-Policy` turns off the camera, microphone and location.
  - `nosniff` and a strict referrer policy round it out.
- **Build settings:** whether search engines may index the site, and the address of the favorites backend.

## Domain and DNS: Route 53

The domain `program-il.com` is registered with AWS, and its DNS lives in **Route 53**. It holds:

- the records that point `itzik`, `www` and the bare domain to Amplify
- a record that proves to AWS I own the domain, so the HTTPS certificate can be issued
- **email records** (MX, SPF, DKIM, DMARC). These let mail to `hi@program-il.com` be forwarded to my inbox, and let the site send email that inboxes trust.

**Why Route 53:** the domain was already registered at AWS, and keeping DNS in the same account lets Amplify and SES add their records automatically.

**Why a subdomain** (`itzik.`)? Each future project gets its own repository and its own subdomain, like `project.program-il.com`. This site is just the first.

## GitHub: the single source of truth

Everything is in one GitHub repository: code, posts, lists and configuration. If it's not in the repo, it's not on the site.

- **Branch protection (a ruleset on `main`)** blocks force-pushes and deleting the branch, so history can't be rewritten or wiped, even by mistake.
- **GitHub Actions** run a small workflow that rebuilds the site **every day** (to pick up GitHub projects I've tagged `portfolio`) and on demand with a "Run workflow" button. It calls an Amplify webhook. The webhook address is a **GitHub secret**, never written in the code.
- **Automated tests** run on my machine before every push: 78 unit tests and 185 browser tests on desktop, iPhone, Android and a small 360px phone. Some tests exist purely for privacy. They fail if a phone number or personal email ever appears in the repo, on a page, or in commit metadata.

## Editing from anywhere: the `/admin` editor

I can write posts from a browser, including on my phone, at `/admin`. It's **[Sveltia CMS](https://github.com/sveltia/sveltia-cms)**, a small open-source editor that runs entirely in the browser and saves by committing to GitHub.

**Why this and not a hosted CMS?** There's no extra server or account, and content stays as Markdown files in my repo. I sign in with a **fine-grained GitHub token** that can only touch this one repository. The editor's script is pinned to an exact version with an integrity hash, so a compromised download can't run. Publishing is just turning **Draft** off: it commits, Amplify rebuilds, and the post is live in a few minutes.

## The one backend: visitor-suggested favorites

The [favorites list](/#favorites) accepts suggestions from visitors through a [small form](/favorites/suggest/). I wanted two guarantees: **a real, verified email address**, and **nothing appears without my approval**. Here is the flow:

1. You fill in the form. The site sends it to a **Lambda function**.
2. The function checks the input and its rate limits, then emails you a confirmation link through **Amazon SES**.
3. You open the link and press **Confirm**. A press is needed because email security scanners open links automatically.
4. The function opens a **pull request** on my repository that adds your link.
5. I get an email, review the pull request (and can edit it), and **merge** to publish it.

The AWS pieces, and why each one:

| Service | What it does here | Why this one |
|---|---|---|
| **AWS Lambda** with a **function URL** | Receives the form and the confirmation | Runs only when called, no server. A function URL is free and simpler than API Gateway for two routes |
| **Amazon SES** | Sends the confirmation email (and my "new suggestion" email) | Cheap ($0.10 per 1,000 emails), and with DKIM and DMARC the mail is signed as program-il.com, so it lands in inboxes, not spam |
| **Amazon DynamoDB** | Counts requests for rate limits (per visitor, per email address, per day) | Pay-per-request, and entries **delete themselves** after at most a day |
| **SSM Parameter Store** | Holds the two secrets: the signing key and the GitHub token | Encrypted, free, readable only by this function |
| **IAM role** | The function's permissions | Least privilege: it can update one table, read two secrets, and send mail from one address. Nothing else |
| **CloudWatch Logs** | The function's logs | Kept 14 days. Logs record outcomes only, never email addresses |
| **CloudFormation** | Creates all of the above from one file in the repo | Repeatable, reviewable, and easy to tear down |

**Privacy by design.** The confirmation link carries the suggestion itself, **digitally signed**, so the backend doesn't need a database of pending suggestions or a list of email addresses. Your email is used once, to send that link, and then forgotten. The rate-limit counters store only scrambled (keyed-hash) values, never your address or IP. The confirmation email deliberately repeats nothing you typed, so the form can't be abused to send spam in my domain's name.

**Why a pull request** instead of an admin dashboard? GitHub already gives me review, editing, history and a phone app. Approving is a merge, and rejecting is closing. Nothing new to build or secure.

## Email: forwarding, not a mailbox

`hi@program-il.com` doesn't have its own mailbox. Mail to it is forwarded to my personal inbox by **ImprovMX** (free tier), using the MX and SPF records in Route 53. **Why:** a full mail service like WorkMail or Google Workspace costs money every month, and for one contact address, forwarding is all I need.

## What it costs

| Piece | Monthly cost |
|---|---|
| Amplify Hosting (builds + traffic) | cents, at personal-site traffic |
| Route 53 hosted zone | $0.50 |
| Domain renewal | yearly, billed once a year |
| Lambda, DynamoDB, SSM, CloudWatch | $0 (free tier) |
| SES | a few cents at most |
| GitHub, Sveltia CMS, ImprovMX | $0 |

## Trade-offs I accepted

- **Content is public before it's published.** The repository is public, so drafts and pending suggestions are visible on GitHub. I'm fine with that for this site.
- **The GitHub token can do more than it needs.** It's limited to this one repository, but GitHub can't restrict a token to opening pull requests only, so it could also push to `main`. It lives only in AWS's encrypted store, and it expires.
- **No database means no "your link was approved" email.** Sending one would mean keeping your address until I decide. I chose to forget it immediately.
- **Rate limits live in code, not in a firewall service.** That's fine at this scale and saves a monthly fee.
